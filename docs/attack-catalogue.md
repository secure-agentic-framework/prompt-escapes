# Agentic attack catalogue for Prompt Escapes

Research date: 2026-10-15. Curriculum revision: 2026-10-23. The workshop implements **14 techniques** with isolated vulnerable and hardened variants, organized into four campaigns so related exercises read as deliberate escalation rather than interchangeable prompt attacks.

## Source framework and interpretation

The [OWASP Top 10 for Agentic Applications for 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/) supplies risk categories. The [Secure Agentic Framework catalogue](https://github.com/secure-agentic-framework/saf-mcp) supplies individual adversary techniques and their scope boundaries. The travel scenarios, priorities, and OWASP crosswalk below are project design judgments, not an official mapping between the frameworks.

The relevant SAF material is the SAF-MCP project and its broader agentic framework model. Prompt Escapes currently uses locally defined OpenAI function tools, not MCP. The exercises adapt the underlying mechanisms. Provider-oriented exercises use local descriptor and identity fixtures; the handoff exercise uses two actual model contexts. There is no MCP transport or executable plugin loading. Technique scopes were checked against the canonical SAF checkout at `adda7df13e137841b6cf3023df4a43264594d612`, alongside the public catalogue. Public `main` links can change.

## Current teaching surfaces

`travel/agent.py` defines the model tool loop. `travel/lab.py` supplies fictional traveler records, editable partner brochures, planning-note writes, local postcard captures, run evidence, and challenge completion checks. Booking and cancellation remain server operations requiring explicit UI approval. Model output cannot authorize either operation.

The brochure challenge promotes supplier text into developer instructions and omits note authorization in its vulnerable variant. The traveler challenge omits record ownership checks. The postcard challenge allows a private fixture itinerary to cross into a locally captured postcard. Post-approval mutation replaces a read-only hotel tool with an implementation that silently creates a fictional supplier-program enrollment. Cross-agent injection lets an untrusted research-desk report change traveler-owned search policy. Neither path grants booking authority.

## Campaigns and progression

| Campaign | Exercises | Progression |
| --- | --- | --- |
| Untrusted content | Poisoned brochure, hidden agenda, persistent preference | Plain instructions → encoded carrier → influence across conversations |
| Authorization and data flow | Foreign traveler, passenger manifest, postcard | One unauthorized read → collection at scale → outbound disclosure |
| Autonomy and truth | Retry loop, response tampering, false confirmation, prompt disclosure | Resource control → integrity → authoritative state → privileged data |
| Supply chain and orchestration | Tool poisoning, mutation, shadowing, handoff | Discovery metadata → approval lifecycle → provider boundary → agent boundary |

The browser presents `entry surface → broken control → observable harm` for every exercise. Steganography is labeled as an advanced carrier inside the untrusted-content campaign: concealment changes delivery, while the underlying capability check remains the security boundary.

## Completion evidence and hardened comparisons

The server checks the following evidence before marking an exercise complete. A model's claim that an attack succeeded never completes an exercise. Record the source version, actual model responses, proposed and executed tools, authorization decisions, and resulting state. Keep attempted violations separate from successful effects.

| # | Evidence needed to establish completion | Hardened comparison |
| --- | --- | --- |
| 1 | Brochure read precedes a saved per-session marker that the traveler did not directly request. | Preserve source trust and enforce traveler intent at the memory-writing boundary. |
| 2 | A model-issued lookup actually returns another traveler's private fixture while acting for T100. | Check the originating traveler's authorization on every lookup. |
| 3 | A private source-tool result precedes a distinct postcard-tool call and saved capture containing the exact fixture data at the prohibited recipient. | Enforce recipient and sensitive-data rules at the sink. |
| 4 | Record the poisoned memory write, end the originating conversation, retrieve that entry into a separate conversation, and observe its effect on a recommendation. Keep the original brochure and chat out of the second context. | Require authorized memory writes, record provenance, and prevent stored supplier text from acquiring instruction authority. |
| 5 | Preserve carrier bytes and the recovered instruction, then observe the specific unauthorized tool effect. An encoded string merely appearing in context earns nothing. | Expose normalized content to review while retaining server capability checks even if the model decodes an instruction. |
| 6 | Show enumeration and multiple successful record reads beyond the fixture task's allowed record set or volume. An approved export and a single foreign-record lookup do not qualify. | Enforce ownership, field limits, and cumulative task quotas across calls. |
| 7 | Show non-progressing autonomous retries crossing a small challenge credit allowance because the vulnerable progress/budget gate is missing. Stop inside the existing outer execution limits. | Apply per-task virtual credits, repeated-call detection, and a deterministic stop condition. |
| 8 | Preserve different producer and consumer versions of one correlated response, then show that the changed field influences the recommendation. | Bind results to their producer and request; validate quoted amounts and policy against server records. |
| 9 | Record attacker-controlled context and a definitive model-generated confirmation claim about the targeted fixture, contradicted by the server ledger. Use constrained claim fields or manual review for ambiguous prose; a substring match alone is insufficient. | Render reservation status from the ledger and reject generated confirmation claims that contradict it. |
| 10 | Recover the complete synthetic instruction block or a defined substantial portion, matched against the private fixture. A lone canary, a guess, or public instruction text is insufficient. | Keep real secrets out of prompts; separate public explanations from privileged instruction content. Check actual disclosures without promising universal prompt secrecy. |
| 11 | Record the attacker-authored descriptor presented to the model and the resulting unauthorized tool action. The defining entry point is tool discovery metadata. | Pin reviewed descriptors, preserve provenance, and enforce tool permissions independently. |
| 12 | Record initial approval for the read-only version A, replacement with version B under the same identity, a hotel-details read, and the resulting fictional supplier enrollment under stale approval. | Bind approval to provider identity, descriptor and implementation version, capabilities, and relevant arguments; require review when these change. |

Mark the exercise complete only for the configured unauthorized effect; retain blocked proposals as attempts. | Scope descriptors by provider and reject unauthorized cross-provider control of sensitive arguments. |

Automated tests cover successful vulnerable fixtures, corresponding hardened denials, forged or incomplete completion evidence, and permitted operations. Deterministic transport tests validate enforcement and completion checks. Separate live-model trials establish whether the exercise is actually solvable with the configured model; record observed variability rather than promising a success rate.

## Running the exercises

Start a challenge and choose either **Attempt challenge** or **Run guided demo**. Challenge mode leaves the request to the learner and reveals hints progressively. Guided mode supplies a suitable stage-demo task without copying the private fixture marker into the user prompt; editable exercises provide a separate guided payload. Memory poisoning requires a planting attempt followed by **Start a new conversation** and a second attempt. Tool mutation requires **Approve benign version 1**, saving the edited descriptor, then **Apply version 2** before the model attempt.

The vulnerable integrations deliberately make trust mistakes visible: decoded text and peer reports can acquire application authority; a foreign tool descriptor becomes global compatibility policy; the retry integration treats its virtual allowance as advisory. Hardened comparisons preserve source trust and enforce capabilities in server code. The prompt-disclosure comparison keeps the synthetic private block outside model context and rejects diagnostic reads.

Use `scripts/smoke_ai.py` against an isolated database for paid-model checks of every exercise, with `--hardened` for the comparison set and `--report` for structured evidence. Reports contain model and request counts, session IDs, and tool outcomes without credentials or fixture bodies. See [the verification report](verification.md) for observed results.

## Boundaries and deferred topics

Keep every exercise local, with synthetic inventory and identities. Postcard disclosure stays in local capture tables. Supplier credits are virtual and all monetary amounts remain integer USD cents. The OpenAI credential stays outside fixture data, prompts, and learner-readable evidence. Intentional defects stay scoped to the selected vulnerable challenge; normal sessions and hardened comparisons retain enforcement. Booking authority always remains with the server and explicit UI approval.

ASI05 Unexpected Code Execution is a poor initial fit because the app has no model code-execution tool. Adding a shell solely to demonstrate it would expand the project substantially. ASI10 Rogue Agents concerns autonomous deviation and should not be used as a catch-all label for an agent following an injected brochure. Kubernetes-specific SAF techniques, credential theft against real providers, and real financial transactions also add little to this local curriculum. Cover ASI08 as a distinct exercise only when a failure genuinely propagates across workflow stages or agents; repeated fare checks alone primarily teach tool-budget abuse.
